# Server Actions Refactoring Notes

Updated Date: 2025-08-31

## High-Level Analysis

The current implementation in `contentActions.ts` and `spaceActions.ts` is functional but suffers from significant code duplication and a lack of type safety. This creates a fragile system where a single change (e.g., to authentication logic) requires updates in many places, increasing the risk of bugs. The heavy use of `any` undermines the benefits of TypeScript, making the code harder to reason about and refactor safely.

## Key Issues & Recommendations

Here is a summary of improvements to be made:

### 1. Reduce Boilerplate with a Centralized gRPC Handler

*   **Problem**: Every server action repeats the same logic for authentication, metadata creation, `Promise` wrapping for the gRPC callback, and `try/catch` error handling. This is a classic violation of the DRY (Don't Repeat Yourself) principle.
*   **Solution**: Create a single, generic, higher-order function to encapsulate this entire lifecycle. This function should be responsible for:
    1.  Verifying user authentication via `auth()`.
    2.  Creating gRPC metadata with the bearer token.
    3.  Executing the gRPC call.
    4.  Converting the callback-based gRPC method into a `Promise`.
    5.  Handling and normalizing gRPC errors and exceptions into a consistent `ActionResult`.
    6.  Logging errors on the server side for better observability.

### 2. Eliminate `any` and Enforce Strong Typing

*   **Problem**: The code is littered with `any`, especially in the gRPC callbacks (`error: any`, `response: any`). This is a major code smell that sacrifices type safety for convenience. It prevents TypeScript from catching potential bugs, makes refactoring risky, and hinders developer tooling like auto-completion.
*   **Solution**:
    *   **Use Generated Types**: Replace `any` with the specific request and response types generated by `protoc` (e.g., `ListSpacesResponse` for responses, `grpc.ServiceError` for errors).
    *   **Type the Mappers**: The helper functions that convert protobuf objects to frontend types (e.g., `protoSpaceToSpace`) should accept a strongly-typed protobuf object instead of `any`.

### 3. Consolidate Shared Utilities

*   **Problem**: Helper functions like `createMetadataWithAuth` and `timestampToISOString` are duplicated across both `contentActions.ts` and `spaceActions.ts`.
*   **Solution**: Move these functions into a shared utility file (e.g., `src/api/grpc-utils.ts`). This ensures that any future modifications or bug fixes only need to be made in one place.

### 4. Rethink Client-Side Authorization Checks

*   **Problem**: The `updateSpace` and `deleteSpace` actions first call `getSpace` to verify ownership. While this works, it results in an extra network request and database query for every update or delete operation (an N+1 problem).
*   **Solution**: The comment `// TODO: Activate RLS...` correctly identifies that authorization should ultimately be handled by the backend. The long-term, secure, and performant solution is to rely on the backend to enforce ownership rules based on the authenticated user's ID passed in the JWT. The client should trust the backend to return a `FORBIDDEN` error if the user is not authorized. The current implementation is an acceptable temporary workaround.
